# ISS-027: Define repeated Runtime Service init semantics

## Metadata
- Type: bug
- Status: closed
- Priority: 1
- Labels: runtime, protocol, lifecycle
- Assignee: unassigned
- Created: 2026-06-02
- Updated: 2026-06-02
- External ref: none

## Description
The official Runtime Service implementation of `POST /init` is not a no-op when called after initialization. If no run is active, repeated init clears and rewrites Runtime secrets, reconfigures Codex credentials, updates the git remote, fetches the source repository, and checks out the requested branch or commit.

That behavior is dangerous if callers accidentally send `/init` to an already ready Runtime Service. It also leaves Runtime Protocol v3 unclear about whether repeated init is forbidden, idempotent, or a reset operation.

## Design
Define and implement explicit repeated-init behavior for Runtime Service v3. The preferred contract is conservative:

- before initialization, `POST /init` initializes the Runtime Service;
- while a run is active, `POST /init` returns `409 Conflict`;
- after initialization and without an explicit reset protocol, repeated `POST /init` must not mutate secrets, credentials, repository state, or workspace contents.

The final implementation can either return the current init response without mutation or return a protocol-level `409 Conflict`; choose one behavior and document it in `docs/runtime-protocol/` and `packages/runtime_protocol`.

## Acceptance Criteria
- [x] Runtime Protocol documentation states the behavior of repeated `POST /init`.
- [x] `packages/runtime_protocol` tests or helpers reflect the chosen repeated-init contract where applicable.
- [x] Official Runtime Service repeated `/init` after initialization does not mutate secrets, credentials, repository state, or workspace contents.
- [x] Official Runtime Service still rejects `/init` while a run is active.
- [x] Runtime Service tests cover first init, repeated init after ready, and init while running.

## Notes
- 2026-06-02: Discovered while checking whether the official Runtime Service `/init` implementation is idempotent.
- 2026-06-02: Implementation started. The chosen contract is idempotent repeated `/init` for identical initialization data, because caller retries should be safe and must not mutate Runtime secrets, credentials, repository state, or workspace contents. Repeated `/init` with different initialization data remains a protocol conflict.

## Close Notes
- 2026-06-02: Defined repeated `POST /init` after initialization as idempotent for identical initialization data. Repeating the same init request returns `200 OK` without mutating Runtime secrets, credentials, repository state, or workspace contents. Repeating `/init` with different initialization data returns `409 Conflict`, and `/init` while a Run is active still returns `409 Conflict`. Added a shared `runtime_service_init_conflict_message()` protocol constant and test. Updated Runtime Protocol README and OpenAPI docs. Updated the official Runtime Service to keep the first init identity and response metadata. Added runtime-service whitebox tests for repeated same init, repeated different init, and init while active.
