## Description
Refactor the admin frontend model so Users, Secrets, and Runtimes state are grouped by page instead of flattened into one large `AdminModel`. The current flat model makes edit/create dialog invariants implicit and will become harder to maintain as Runtime Config and Source Host state grows.

## Design
Introduce small page state records such as `AdminUsersState`, `AdminSecretsState`, and `AdminRuntimesState`. Replace loose runtime editor fields like `creating_runtime`, `editing_runtime_id`, `editing_runtime_name`, and `editing_runtime_config_json` with a single optional Runtime editor state. Do the same for Secret create/edit/delete state where it reduces coupling. Keep behavior and styling unchanged.

## Acceptance Criteria
- [x] `AdminModel` groups Users, Secrets, and Runtimes state into cohesive child records.
- [x] Runtime create/edit form state is represented by one explicit editor object.
- [x] Secret create/edit/delete state is grouped or made explicit without changing UI behavior.
- [x] Existing admin UI behavior and visual style are unchanged.
- [x] Frontend/admin tests and `moon test --warn-list +73` pass.
