# ISS-029: Remove per-request preview readiness preflight

## Metadata
- Type: bug
- Status: open
- Priority: 1
- Labels: backend, runtime, preview
- Assignee: unassigned
- Created: 2026-06-02
- Updated: 2026-06-02
- External ref: none

## Description
For every public preview request, the control-plane calls `RuntimeGateway::project_runtime_preview()`. That method ensures the Runtime Service and then calls Runtime Service `GET /preview` as a readiness check before the control-plane proxies the actual browser request.

`GET /preview` is not a pure status endpoint. It enters the Runtime Service preview content handler and can trigger preview startup through `ensure_preview()`. The actual browser request then enters Runtime Service `/preview/...` again and calls `ensure_preview()` a second time.

This makes one user preview request perform duplicated Runtime preview work.

## Design
Stop treating Runtime Service `GET /preview` as a per-request readiness preflight. The control-plane should ensure the Runtime Service container is healthy and initialized, then directly proxy the actual preview request. Runtime Service remains responsible for lazy preview startup and preview content readiness.

Do not add a new protocol endpoint in this issue. A dedicated preview status endpoint can be considered in a future Runtime Protocol revision if needed.

## Acceptance Criteria
- [ ] A public preview request no longer performs an extra Runtime Service `GET /preview` before proxying the requested path.
- [ ] Runtime Service lazy preview startup still happens when the preview process is cold.
- [ ] Preview TTL refresh behavior is preserved for successful preview responses.
- [ ] Existing smoke preview health flow still passes.
- [ ] Tests cover that the control-plane computes the preview proxy target without content-endpoint preflight.
