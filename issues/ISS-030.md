# ISS-030: Separate preview cache policy from Runtime API cache policy

## Metadata
- Type: bug
- Status: open

- Assignee: unassigned
- Created: 2026-06-02
- Updated: 2026-06-02

## Description
Runtime Service `send_reply()` adds `Cache-Control: no-store` to all Runtime Service responses. This is appropriate for Runtime API endpoints such as `/health`, `/init`, `/exec`, `/runs/:run_id`, and `/runs/:run_id/events`.

Preview content should not inherit the same blanket cache policy. Generated previews may include large JS, CSS, image, WASM, or vendor assets. If every preview resource is treated as uncacheable, repeated preview opens and reloads cannot reuse stable assets.

The current preview proxy path also preserves only a small response-header subset, so cache validators and upstream preview cache policy can be lost.

## Design
Split cache policy by response class:

- Runtime API responses remain `Cache-Control: no-store`.
- Preview HTML shell responses use `no-store` or `no-cache`.
- Content-hashed static assets may use long-lived immutable caching.
- Non-hashed assets use conservative `no-cache` or a short TTL.
- Runtime Service and control-plane forward safe preview response headers, including `Content-Type`, `Cache-Control`, `ETag`, and `Last-Modified`.

Do not let arbitrary upstream headers escape through the proxy without review.

## Acceptance Criteria
- [ ] Runtime API endpoints still return `Cache-Control: no-store`.
- [ ] Preview content responses are no longer forced through the Runtime API blanket `no-store` policy.
- [ ] Safe preview cache headers are preserved through Runtime Service and control-plane proxying.
- [ ] Tests cover API cache headers and preview cache-header forwarding separately.
- [ ] Smoke or targeted preview checks verify cache headers for preview root and at least one static asset path.
