# ISS-024: Remove Runtime Config from user-facing project DTOs

## Metadata
- Type: bug
- Status: open
- Priority: 1
- Labels: api, frontend, sdk, runtime, architecture
- Assignee: unassigned
- Created: 2026-06-01
- Updated: 2026-06-01
- External ref: packages/sdk/sdk.mbt

## Description
The user-facing `ProjectDetail` response currently includes `runtime_config`. That leaks admin/runtime launcher internals into the main app API and forces the user frontend to decode `RuntimeConfig`.

This caused a real failure on `craft-test.moonbitlang.com`: project creation succeeded, but the frontend reported `Failed to create project. Unexpected response.` because the response contained a Runtime Config shape that the frontend could not decode. The project and GitHub source repository were created successfully, so the error was purely an API DTO boundary problem.

## Design
Split user-facing project DTOs from admin diagnostic DTOs. The main app should receive only user-visible project fields: ids, display name, runtime id/name, status/activity, source repository metadata, preview, and timestamps. It should not receive or decode Runtime Config. Admin APIs may expose Runtime Config through admin-only response types.

Do not solve this with cache headers, app-version handshakes, or generic decode-failure copy. Those can be useful separately, but the root fix is to remove internal Runtime Config from user-facing responses.

## Acceptance Criteria
- [ ] User-facing `ProjectDetail` no longer contains `runtime_config`.
- [ ] Main app frontend no longer decodes `RuntimeConfig` when listing, loading, creating, or updating projects.
- [ ] Admin project diagnostics still expose Runtime Config where needed through an admin-only DTO.
- [ ] Create-project success responses cannot fail solely because Runtime Config schema changed.
- [ ] Tests cover user-facing project responses without Runtime Config and admin diagnostics with Runtime Config.
