# ISS-028: Make Runtime preview startup single-flight

## Metadata
- Type: bug
- Status: closed
- Priority: 1
- Labels: runtime, preview, concurrency
- Assignee: unassigned
- Created: 2026-06-02
- Updated: 2026-06-02
- External ref: none

## Description
Runtime Service preview startup calls `ensure_preview()` before proxying to the generated app preview process. `ensure_preview()` checks readiness, stops any tracked preview process, starts `mooncraft-preview.sh`, and waits for readiness.

There is no concurrency guard around this flow. If multiple browser resource requests arrive while the preview is cold or restarting, they can all observe the preview as not ready and race through stop/start/wait. This can cause duplicate starts, accidental process termination, readiness flapping, and non-deterministic preview failures.

## Design
Make Runtime Service preview startup single-flight. Only one preview startup attempt may run at a time. Concurrent preview requests should wait for the in-flight startup result instead of starting or stopping the preview process themselves.

Keep lazy preview startup in the Runtime Service. Do not move preview process ownership back to the control-plane.

## Acceptance Criteria
- [x] Concurrent preview requests cannot start multiple preview processes for the same Runtime Service.
- [x] Concurrent preview requests wait for the same in-flight startup result.
- [x] Once the preview is ready, preview requests proxy without restarting the process.
- [x] Failed startup still exposes preview log or exit-status detail.
- [x] Runtime Service tests cover concurrent cold preview requests.
